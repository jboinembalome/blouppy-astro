Most .NET test projects created from a template reference `coverlet.collector`. Few of them ever produce a coverage report, and the ones that do often show one percentage on a badge nobody reads twice. When somebody does read it, the question is usually the wrong one: "is 80% enough?".

Coverage measures which lines ran. It does not measure what the tests checked.


## Two runners, two ways to collect
Since .NET 10, `dotnet test` runs on one of two platforms, and the coverage tool depends on which one.

With **VSTest**, the historical runner, coverage is a *data collector*. The `coverlet.collector` package plugs into it. With **Microsoft.Testing.Platform** (MTP), each test project is an executable that runs its own tests, and VSTest collectors are not loaded. Coverage comes from an MTP extension instead, Microsoft's `Microsoft.Testing.Extensions.CodeCoverage` (coverlet also ships `coverlet.MTP`):

```bash
# VSTest, with coverlet.collector
dotnet test --collect "XPlat Code Coverage"

# Microsoft.Testing.Platform, with Microsoft.Testing.Extensions.CodeCoverage
dotnet test -- --coverage --coverage-output-format cobertura
```

A solution opts into MTP with `"test": { "runner": "Microsoft.Testing.Platform" }` in its `global.json`. The two worlds do not mix. An MTP test application rejects options it does not know, so `--collect` fails the run instead of being ignored.


## The trap: a collector that cannot run
[Blouppy Starter](https://starter.blouppy.com/) fell into exactly this gap. Its `global.json` selected MTP, while every test project still referenced `coverlet.collector`, as the template left it. Nothing collected coverage, and the collector could not have: running a project with `--collect` stopped with `error: unknown option: --collect` and zero tests run. Nobody asked for coverage, so nothing broke. The reference only suggested that something was measured.

The fix replaced `coverlet.collector` with `Microsoft.Testing.Extensions.CodeCoverage` in every test project. Every project needs it, because passing `--coverage` to one without the extension fails on the unknown option. The Starter adds the reference to each `.csproj`. A project-management app built on the Starter does it once, in `Directory.Build.props`:

```xml
<ItemGroup Condition="'$(IsTestProject)' == 'true'">
  <PackageReference Include="Microsoft.Testing.Extensions.CodeCoverage" />
</ItemGroup>
```

The condition works even though `IsTestProject` is set in each `.csproj`, because MSBuild evaluates every property before any item. Each run with `--coverage` then writes one Cobertura file per test project.


## One report from many files
One file per test project is not a report. The same assembly shows up in many of them: a shared kernel is loaded by almost every test project, each covering a different part. [ReportGenerator](https://reportgenerator.io/) merges the hits per line. The Starter's CI does not run this step yet; here is how it could look after the test step:

```yaml
- name: Coverage report 📊
  if: always()
  run: |
    dotnet tool install --global dotnet-reportgenerator-globaltool
    reportgenerator \
      -reports:"TestResults/*.cobertura.xml" \
      -targetdir:"TestResults/coverage" \
      -reporttypes:"Html;MarkdownSummaryGithub" \
      -assemblyfilters:"-*.TestHelpers" \
      -filefilters:"-*/Migrations/*"
    cat TestResults/coverage/SummaryGithub.md >> "$GITHUB_STEP_SUMMARY"
  working-directory: back
```

`MarkdownSummaryGithub` writes a table shaped for the run's [job summary](https://docs.github.com/actions/writing-workflows/choosing-what-your-workflow-does/workflow-commands-for-github-actions#adding-a-job-summary), one click from the pull request, with no third-party service and no token.

The two filters matter. EF Core migrations start with `// <auto-generated />`, but that comment is not an attribute, so they are instrumented like any other code. A database test fixture applies every migration, so thousands of `CreateTable` lines count as covered and prove nothing. Test helper libraries are the other distortion. For code left untested on purpose, such as a composition root, `[ExcludeFromCodeCoverage(Justification = "...")]` takes a type out. Keep it rare: hiding a hard class is the cheapest way to raise a number.


## Read the branch figure first
A report gives two figures. Line coverage counts the lines that ran at least once. Branch coverage counts, at each decision, the outcomes that were taken. The second is the more honest one.

The Starter strips the secrets from a webhook URL before the audit log keeps it (null check left out):

```csharp
public static string UrlWithoutSecrets(string url)
{
    if (Uri.TryCreate(url, UriKind.Absolute, out var uri))
    {
        return uri.GetComponents(
            UriComponents.Scheme | UriComponents.Host | UriComponents.Port | UriComponents.Path,
            UriFormat.UriEscaped);
    }

    var end = url.IndexOfAny(['?', '#']);

    return end < 0 ? url : url[..end];
}
```

Its test is a theory with five absolute URLs. The method reports **80% of lines and 25% of branches**. Every input parses, so the fallback for a relative string never runs. That is two lines out of ten, but three of the four branch outcomes. The line figure says "nearly done"; the branch figure says half the behaviour was never tried. One `[InlineData]` with a relative path closes it.

Branches also hide where a line count flattens them: `??`, `?.`, a `switch` expression and a short-circuit `&&` sit on one line and can be half-tested.


## What the number does not say
Coverage records that a line ran during a test, not that anything was checked. Remove the assertion from that theory and the test stays green, with the same 80%. If the method returned the URL untouched, token included, it would still pass. A test that asserts the wrong thing, or a mock never verified, fails the same way, less visibly.

So coverage is good at one job: finding code that **no test runs at all**. That is a certain gap. A covered line is only a possible check. Mutation testing, with a tool such as Stryker.NET, covers the other half: it changes the code and reports the changes no test noticed.

That is also why a global threshold is a weak gate. The percentage moves for reasons unrelated to the change: deleting well-tested code lowers it, adding a migration raises it. A developer blocked at 59.8% writes the test that runs the most lines, rarely the one that checks the most. Showing the number on each pull request and reading the uncovered lines of the files it touches does more. For a small project, running `--coverage` locally now and then and opening the HTML report is enough.
